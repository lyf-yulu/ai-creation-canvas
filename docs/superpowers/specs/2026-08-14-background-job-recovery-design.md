# 后台任务可靠完成设计

## 目标

AI 创作画布以公司内部、单实例部署为当前目标。对具备服务端恢复能力的供应商，用户关闭画布、切换页面或关闭浏览器后，已经提交的图像和视频任务仍必须继续轮询，并在完成后把全部结果、任务状态和费用快照可靠写入服务端；服务进程重启后，未完成任务必须能够从 SQLite 继续恢复。现有 Cookie 型 Portal 缺少服务端认证轮询协议，因此作为明确的在线兼容例外处理，不伪称具备离线恢复能力。

本切片不建设 Redis 持久消息队列，也不承诺多实例之间的任务接管。现有 Redis 继续承担模型线路和凭据并发协调；SQLite 是后台轮询任务的事实来源。

## 核心原则

- 默认情况下，浏览器只提交任务和读取状态，不负责推动任务状态机。
- 现有 Cookie 型 Portal 是受控兼容例外：它不保存浏览器 Cookie，也不伪装成可后台恢复；仅在任务所有者保持登录并读取该任务时，使用当前请求 Cookie 推进一次 Portal 轮询。
- worker 只轮询已经获得明确上游任务 ID、且适配器声明可由服务端恢复的 `queued` 或 `running` 任务。
- `submission_unknown` 不自动重提，也不自动跨 Key 或线路恢复，避免重复扣费。
- 后台轮询使用服务端保存的用户归属、不可变线路快照和凭据指纹；不得接受浏览器自报身份。
- 一次供应商完成可以产生 1–15 个结果，必须作为一个原子状态更新保存。
- 费用快照只在任务第一次成功落库时生成一次。
- 本地恢复记录只能在数据库确认成功结果后清除。

## 架构

### 后台轮询服务

新增一个与 HTTP API 无关的任务轮询服务，负责：

1. 从 `CanvasStore` 领取一项可轮询任务。
2. 根据任务类型解析适配器：
   - 普通任务从 `AdapterRegistry` 解析；
   - 逻辑模型任务从不可变 route snapshot、当前受限凭据池和原 key fingerprint 解析。
3. 调用供应商 poll 接口。
4. 验证全部结果 ID、状态与错误类型。
5. 通过带租约 token 的 CAS 更新写入任务状态。
6. 数据库成功后调用适配器的结果确认钩子，清理本地 pending 元数据。

HTTP `GET /jobs/{id}` 对具备服务端恢复能力的适配器只读取并返回当前状态。Cookie 型 Portal 适配器显式声明 `requires_request_scoped_polling`，不进入 worker 队列；所有者读取其 `queued/running` 任务时，服务端才用当前请求 Cookie 执行一次轮询并按同一结果校验与原子写入合同保存状态。跨用户请求仍先按任务归属返回 404，不接触 Portal。

该兼容模式不持久化 Cookie，不允许后台 worker 使用浏览器身份，也不承诺用户关闭浏览器后继续推进 Portal 任务。用户重新登录并打开任务后可以继续轮询。Ark、Chiyun、受管线路及其他具备服务端恢复能力的适配器仍严格使用后台 worker，GET 不得对它们执行供应商 I/O。

### 应用内 worker

FastAPI 生命周期启动一个应用内 worker。worker 每次只领取一项任务，并使用 SQLite 租约避免重复处理。轮询期间按租约时间的三分之一续租；停止服务时取消当前轮询并释放租约。多个测试 lifespan 或意外重复启动不能跨事件循环等待同一个任务。

worker 默认用于单实例。若未来改为多个实例，SQLite CAS 仍能阻止同一时刻重复写入，但跨实例吞吐、队列公平性和进程崩溃调度应升级为独立的持久队列，而不是继续扩展本 worker。

### SQLite 状态与租约

`CanvasStore` 提供以下明确边界：

- `claim_pollable_job(lease_seconds)`：只领取有上游任务 ID 的 `queued/running` 任务；过期租约可被重新领取。
- `renew_job_lease(job_id, token, lease_seconds)`：只有当前持有者可续租。
- `release_job_lease(job_id, token, retry_after_seconds)`：临时失败或进程关闭后延迟重试。
- `record_polled_job(..., result_ids)`：按 token 做 CAS，原子保存 1–15 个结果和终态；旧 worker 不能覆盖新租约。

逻辑模型任务和可后台恢复的普通任务进入同一个租约队列，但适配器解析方式不同。Cookie 型 request-scoped Portal 任务不进入 worker 队列。`submission_unknown`、`submitting`、`succeeded`、`failed` 和没有上游任务 ID 的记录都不会被领取。

## 逻辑模型线路

逻辑模型任务必须复用提交时保存的 route snapshot，不读取当前线路配置来改变供应商、模型或调用合同。worker 每次轮询前验证：

- route snapshot 版本受支持；
- 任务的逻辑模型、线路、操作和服务标识与 snapshot 一致；
- 当前池中仍存在 fingerprint 完全匹配的原凭据；
- Provider、逻辑模型和线路仍满足受信调用合同。

若原凭据暂时不可用，任务保留 `queued/running` 状态并延后轮询，不切换到其他 Key。已经落盘的结果不依赖凭据，可继续由原用户下载。

## 结果与 Ark 恢复记录

轮询返回 `succeeded` 时必须存在 1–15 个唯一、安全格式的结果 ID。worker 一次性写入 `result_id`（第一项）和 `result_ids_json`（完整有序列表）。任何一个结果非法都使任务进入 `INVALID_UPSTREAM_RESULT`，不保存部分成功。

Ark 图像任务的本地 pending 文件可能包含尚未写入数据库的结果定位信息。适配器的 `poll` 不再提前清除 pending；只有 worker 确认 CAS 成功且数据库中的结果与本次轮询一致后，才调用 `acknowledge_poll_result`。如果进程在写库前退出，重启后仍可重新下载并写入；如果写库成功后清理失败，重复清理必须安全。

## 错误处理

- 供应商明确返回终态失败：保存供应商的安全错误码并结束任务。
- 结果 ID、数量或媒体合同非法：保存 `INVALID_UPSTREAM_RESULT` 并结束任务。
- 明确不可重试的轮询请求错误：保存受控终态错误，不无限重试。
- 网络错误、限流、凭据协调暂不可用或其他可重试错误：释放租约并延后重试，不改变已保存上游任务 ID。
- worker 自身异常：只记录不含 Key、提示词和素材的结构化安全日志；主循环继续运行。
- `submission_unknown`：保持人工/原任务查询处置，不进入后台自动轮询或重提。
- 直连提交若在供应商是否已经接收方面存在歧义（取消、读写超时、连接中断、无法分类的异常或适配器明确返回 `SUBMISSION_UNKNOWN`），必须原子保存为 `submission_unknown`；同一幂等键不得再次发出供应商提交。只有能够证明请求未提交的错误才可释放 reservation。

## 前端行为

前端 `waitForJob` 保留 AbortSignal、无默认两分钟截止时间和有上限的指数退避。对后台可恢复任务，它只控制 UI 等待，不影响服务端推进；用户离开画布后任务仍由 worker 完成。对 Cookie 型 Portal 兼容任务，它的所有者 GET 会推进轮询；离开页面后暂停，重新登录并打开任务后继续。再次进入项目时读取 SQLite 终态并补建结果节点。

## 数据与仓库边界

`.local-real-media-data/` 是本地真实供应商验证数据，包含 SQLite、pending 元数据和生成文件，不得提交。仓库忽略规则应显式覆盖该目录。生产代码、测试和设计文档可以提交；任何 Key、真实请求原文、完整敏感提示词和结果文件都不得进入 Git。

## 验证

自动化验证至少覆盖：

1. 浏览器关闭后，启动时 worker 完成遗留任务。
2. 服务重启后，过期租约可重新领取；并发 worker 只有一个有效 token。
3. 慢轮询期间续租，旧 token 不能覆盖新 token。
4. 普通任务与逻辑模型任务都能恢复。
5. 逻辑模型严格使用原 route snapshot 和原凭据 fingerprint；凭据缺失时不换 Key。
6. 1 个和多个结果均完整、有序、原子保存。
7. 结果写库前退出时 Ark pending 保留；写库成功后才清理。
8. 永久错误终止、临时错误延后、`submission_unknown` 不重提。
9. 成功回调重复执行仍只有一份费用快照。
10. 两个用户之间任务、结果和费用不可见。
11. 前端轮询支持取消、退避和长任务；仅 Cookie 型 Portal 兼容任务由所有者 GET 推进，其余任务的 GET 保持供应商 I/O 为零。
12. `.local-real-media-data/` 不出现在 Git 状态和发布产物中。
13. Cookie 型 Portal 图片、视频和人像任务可提交、在线完成并生成结果；浏览器 Cookie 不写入 SQLite、日志或后台 worker。
14. 直连提交出现歧义后，同一幂等键重复请求不会再次调用供应商。

完成标准为完整 Python 与前端测试、类型检查、生产构建、安全扫描和发布差异检查全部通过。真实供应商验证只使用隔离测试目录与专用账号，不以本地生成文件作为可提交产物。

## 非目标

- Redis Streams、Celery 或其他多实例持久任务队列。
- 自动重提 `submission_unknown`。
- 使用不同 Key 接管已经提交的供应商任务。
- 修改模型提交、计费价格或管理员模型配置体验。
- 为 Portal 新增或伪造服务端身份令牌；真正的离线 Portal 恢复留给后续受信服务端认证协议。
- 提交本地真实媒体、数据库、凭据或日志。
