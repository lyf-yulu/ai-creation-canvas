# 模型中心路由与分组凭据池设计

**日期：** 2026-08-12

**状态：** 待用户书面审阅

**目标：** 将当前以 Provider 为中心、只支持单一图片模板的模型注册表，演进为以逻辑模型为最终入口、可挂载多条官方或第三方线路、并在严格分组边界内轮询多把 Key 的受控架构。

## 1. 背景与问题

当前实现已经具备管理员 Provider/模型创建、用户授权、服务端凭据引用、SQLite 幂等快照和 Redis 执行许可，但存在三个产品缺口：

1. 管理页面不能录入 Key，也没有清楚展示应如何配置凭据。项目决定按生产规格处理：Key 只存放在仓库外或 Git 忽略的本地受限文件中，不允许通过应用页面写入。
2. 服务端只有 `chiyun_gpt_image_edit_v1` 图片模板，适配器工厂也只构造 Chiyun 图片适配器，因此管理员不能创建视频、文本或其他图片协议模型。
3. 后端虽然已有更新接口，前端没有对象列表、编辑、停用、归档、恢复和条件删除流程。

更根本的问题是当前模型直接归属于一个 Provider 和一个凭据引用。实际业务的最终落点是“逻辑模型”：同一个 Nano Banana 模型可以同时有官方线路、T8Star `gemini` 分组线路和其他第三方线路。用户只应选择 Nano Banana，不应理解供应商、分组或 Key。

## 2. 已确认的产品原则

- 用户只选择逻辑模型和模型参数，不选择 Provider、线路、分组或 Key。
- 一个逻辑模型可以有多条官方或第三方调用线路。
- 每条线路绑定一个凭据池；凭据池属于确定的 Provider、分组和能力域。
- 同一 Provider 的不同分组必须强隔离。例如 T8Star `cc` 分组只能访问 Claude，不能为 Banana 任务提供轮询 Key；`gemini` 分组可服务 Banana，但不能因此访问 Claude。
- Key 只能在满足同一逻辑模型、操作、协议和分组能力的候选池内轮询。
- Key 不进入数据库、浏览器、Redis、日志、任务请求快照或 API 响应。
- 对象默认先停用、再归档；无引用时允许物理删除，有历史引用时销毁运行配置和凭据引用但保留最小审计快照。
- 不允许管理员提供 Python/JavaScript、动态模块路径或任意参数映射脚本。
- 先完成当前图片/视频能力的模型中心迁移，再增量增加价格路由、模型发现和更多协议。

## 3. 领域模型

### 3.1 LogicalModel：逻辑模型

逻辑模型是用户授权、画布目录和任务提交的唯一模型身份。

主要字段：

- `model_id`：稳定且不可复用的内部 ID。
- `display_name`、`introduction`。
- `modality`：`image`、`video` 或 `text`。
- `operation_contracts`：操作、命名输入端口、输出媒体、统一参数 JSON Schema。
- `enabled`、`archived_at`、`revision`。
- `created_at`、`updated_at`。

用户权限只关联 `LogicalModel.model_id`。同一个画布模型节点在不同线路之间调度时，其公开能力、输入端口和参数语义不得改变。

### 3.2 Provider：供应商

Provider 只描述服务边界，不直接代表用户可选模型。

主要字段：

- `provider_id`、显示名。
- 受信协议族，例如 Ark、OpenAI Images、OpenAI-compatible Chat 或受控异步视频协议。
- 默认 HTTPS Base URL、超时、重定向策略和 Provider 级并发上限。
- `enabled`、`archived_at`、`revision`。

Provider 不保存 Key，不保存第三方分组的模型权限，也不直接分配给用户。

### 3.3 CredentialPool：凭据池

凭据池只存在于服务器受限配置中，数据库仅保存其不可逆引用和配置版本摘要。

示例：

```yaml
version: 1
pools:
  nano-banana-official:
    provider: google
    group: official
    allowed_families: [nano-banana]
    keys:
      - id: official-01
        api_key: "由管理员部署"

  nano-banana-t8-gemini:
    provider: t8star
    group: gemini
    allowed_families: [gemini, nano-banana]
    keys:
      - id: t8-gemini-01
        api_key: "由管理员部署"
      - id: t8-gemini-02
        api_key: "由管理员部署"
```

约束：

- 配置文件必须是普通文件、拒绝符号链接，权限必须限制为服务账号读取；生产启动时权限或路径不合格即拒绝启动。
- Key ID 只是池内稳定标识，不得包含 Key 片段。
- `provider`、`group`、`allowed_families` 与 Key 同属一个不可拆分的安全边界。
- Ark 等无供应商分组的官方池可以使用 `group: official`，不发送额外分组字段。
- 分组是否需要随请求发送由受信协议适配器固定决定；管理员不能自定义任意 Header、URL 或代码。
- 配置热重载采用“完整解析与验证后原子替换”；失败继续使用旧版本并产生受控告警。

### 3.4 ModelRoute：模型线路

线路把一个逻辑模型映射到一个具体提供方调用方式。

主要字段：

- `route_id`、`model_id`、`provider_id`。
- `provider_model_name`：供应商精确模型 ID/版本。
- `adapter_type`：来自服务端允许列表。
- `credential_pool_ref`：凭据池引用，不是具体 Key。
- `family`：用于与凭据池 `allowed_families` 交叉验证。
- `operation_contracts`：该线路真实支持的操作、输入和参数映射。
- `priority`、线路并发上限、`enabled`、`archived_at`、`revision`。

线路只有在以下条件全部成立时才可参与任务：Provider、逻辑模型和线路均启用；凭据池存在；Provider、分组、family 匹配；操作和所有参数均可无损映射；输入数量与媒体类型符合线路限制。

逻辑模型公开合同不简单取所有线路的交集，也不允许某条线路静默丢参数。管理员保存线路时必须通过合同兼容性校验；任务筛选时再按本次实际操作和参数选择兼容线路。如果某项公开能力只有部分线路支持，不支持该能力的线路不会参与对应任务。

## 4. 受信模板与多协议适配器

协议适配器负责 HTTP 语义，模型模板负责产品能力，两者分离。

首个增量切片支持仓库已有并经过合同测试的能力：

- Ark 官方图片生成与参考图编辑。
- Ark 官方文生视频、首尾帧和图片参考视频。
- Chiyun / OpenAI Images 风格的图片生成与多参考图编辑；每个已验证端点使用独立受信模板。
- 现有提示词 Skill 的文本模型保持独立服务端配置，本切片只为后续逻辑文本模型预留领域接口，不把未经验证的聊天协议伪装成已支持。

模板由服务端代码注册，声明：

- 模态和允许的操作。
- 输入端口及数量上限。
- 参数 Schema、默认值和固定映射。
- 输出媒体合同。
- 幂等、轮询、取消和恢复能力。

新增供应商时增加受控适配器或复用已经验证的协议适配器；新增模型时增加逻辑模型和线路对象。数据库值不能触发动态导入，也不能携带执行脚本。

## 5. 路由、Key 选择与幂等

任务提交顺序：

1. 再次验证用户仍拥有逻辑模型权限。
2. 根据逻辑模型、操作、输入和参数筛选兼容线路。
3. 排除禁用、归档、不健康或凭据池不可用的线路。
4. 按管理员优先级、线路健康度和当前占用选择线路。
5. 只在线路绑定的凭据池内，通过 Redis 原子租约选择可用 Key。
6. 在 SQLite 中固化逻辑模型、线路、池版本、不可逆 Key 指纹和规范化请求快照。
7. 调用提供方，安全释放租约，并进入现有轮询与结果代理流程。

Key 轮询规则：

- 每把 Key 维护并发上限、短期速率限制、健康状态和熔断截止时间。
- 默认使用“可用 Key 中最少占用，稳定顺序打破平局”，避免随机选择导致不可复现。
- 连接尚未建立、明确限流、明确临时不可用且提供方确认未创建任务时，可在同池选择下一把 Key。
- 鉴权失败将该 Key 标记为不可用并告警；不能无限重试。
- 参数错误、模型不存在、内容审核或其他业务拒绝不换 Key。
- 池耗尽时返回明确的可重试容量错误，不跨分组借 Key。

跨线路规则：

- 只有确定未创建提供方任务时，才可以按优先级尝试下一条兼容线路。
- 如果提供方支持幂等键，所有安全重试继续使用同一个提供方幂等键。
- 请求已经发出但响应未知时，不自动换 Key或线路重发；任务进入 `submission_unknown`，由恢复查询或管理员处理，防止重复扣费。
- SQL 唯一约束仍是平台幂等的最终依据；Redis 只保存短期租约、计数和健康状态。

## 6. 管理页面

管理页面按“逻辑模型 → 调用线路 → 凭据池状态”组织，不再把 Provider 表单当成最终模型入口。

### 6.1 逻辑模型列表与编辑器

- 创建、选中、编辑显示名、介绍、模态和受信能力模板。
- 展示启用、停用、归档和线路健康汇总。
- 保存时携带 revision；冲突返回 409 并要求刷新，不静默覆盖。
- 用户授权页面只显示逻辑模型。

### 6.2 线路列表与编辑器

- 为选中的逻辑模型新增官方或第三方线路。
- 选择 Provider、适配器模板、精确模型 ID、凭据池、family、优先级和并发上限。
- 页面从服务端只获取池 ID、Provider、分组、family、Key 总数/可用数和健康摘要；永不获取 Key。
- 保存前显示合同差异：缺失操作、参数不能映射或输入上限不足时拒绝启用。

### 6.3 生命周期操作

- **停用：** 立即阻止新任务；既有任务仍可按不可变快照轮询和读取结果。
- **归档：** 默认列表隐藏，可恢复；归档前自动停用。
- **直接删除：** 仅从未被线路、权限、任务或画布引用的对象允许。
- **历史对象清理：** 已有引用时删除活动配置和凭据池引用，但保留 ID、显示名、版本、类别、时间和审计事件；不保留 Key、Base URL 或可继续调用的配置。
- **Provider 删除：** 存在未处理线路时拒绝，不执行级联删除。
- **凭据池撤回：** 配置文件删除或禁用后，新任务立即不再使用；引用线路显示不可用，历史任务保留不可逆池版本摘要。

## 7. 数据迁移与兼容

采用增加表和双读迁移，不原地破坏当前数据：

1. 新增逻辑模型、线路和引用/归档字段。
2. 将当前每个 `canvas_models` 记录迁移为一个逻辑模型和一条线路，保留模型 ID、用户授权和 revision 来源。
3. 当前 `credential_ref` 转换为一个凭据池引用；管理员必须在本地配置文件中提供同名池后线路才健康。
4. 迁移期间目录读取优先新结构；未迁移数据只读兼容，不允许新旧两套同时写同一模型。
5. 迁移成功后写入 schema marker，重复启动必须幂等。
6. 不删除旧表；一个发布周期后再通过单独设计决定是否清理。

当前 Chiyun 离线验收模型会迁移为一个图片逻辑模型和一条 Chiyun 图片编辑线路。现有 Ark 静态目录在本切片中通过只读桥接暴露为逻辑模型；管理员要编辑它们时必须先执行显式“导入为受管模型”，避免启动配置与数据库双写。

## 8. 错误处理与可观察性

面向用户的错误保持受控：模型未授权、无兼容线路、凭据池不可用、容量不足、请求被拒绝、提交状态未知、结果失效。不得返回供应商原始正文、Key、分组内部值或 Base URL。

管理员可以看到：

- 逻辑模型和线路状态。
- 池 ID、分组说明、Key 总数/可用数/熔断数。
- 最近一次健康检查时间和安全错误码。
- 哪个参数或输入导致线路不兼容。
- revision 冲突和删除阻塞引用类型。

审计记录创建、更新、停用、归档、恢复、删除、线路优先级变化和用户授权变化。日志只记录稳定对象 ID、不可逆 Key 指纹、请求 ID、错误码和耗时；不记录提示词、媒体、Cookie、Key 或供应商正文。

## 9. 并发与部署边界

- 本地 1–2 人验证使用与生产相同接口的内存协调器。
- 生产启用受管线路时必须配置 Redis。
- Redis 原子管理全站、Provider、线路、用户和 Key 五级租约；Key 选择与占用更新必须在一段 Lua/事务中完成。
- 租约包含过期时间和所有者 token，释放采用 compare-and-delete；长任务提交阶段需要续租或足以覆盖提交超时的 TTL。
- Redis 故障时生产提交 fail closed，不绕过并发控制直接调用提供方。
- 当前 Redis 仍不是持久化后台队列。本切片不承诺进程崩溃后的任务接管；后续可在不改变模型/线路合同的前提下增加 Redis Streams 或独立 worker。

## 10. 测试与验收

### 10.1 领域和存储

- Provider、逻辑模型、线路和池引用的创建、更新、版本冲突、迁移和审计。
- 图片/视频/文本类别和操作不可交叉。
- 分组/family 不匹配的线路无法启用。
- 有引用对象不能直接删除；停用、归档、恢复和最小审计快照正确。

### 10.2 路由和幂等

- Nano Banana 可以从官方线路或 T8Star `gemini` 线路选择。
- T8Star `cc` Key 永远不能进入 Banana 候选池。
- 同池多 Key 在 Redis 中按限制轮询；并发请求不会超额选择同一 Key。
- 明确限流可以安全换 Key；参数/审核错误不会换 Key。
- 模糊超时进入 `submission_unknown`，不会跨 Key或线路重复提交。
- 相同用户和幂等键仍只产生一个平台任务和最多一个不确定提供方提交。

### 10.3 API 和 React

- 普通用户 API 不暴露 Provider、线路、分组、池或 Key。
- 管理员只能看到安全的池状态摘要。
- 逻辑模型和线路可创建、编辑、停用、归档、恢复及条件删除。
- 409 revision 冲突有明确界面反馈。
- 图片、视频和文本模型只出现在对应画布节点或功能入口。
- 只有图片编辑线路时，图片节点仍能正确创建 `image.edit` 操作。

### 10.4 端到端离线验收

使用真实 FastAPI、SQLite、Redis fake/测试实例、React 和 Chromium：

- 管理员创建 Nano Banana 逻辑模型。
- 挂载官方和 T8Star `gemini` 两条模拟线路；另配置一个 T8Star `cc` 池作为负例。
- 为用户授权逻辑模型并提交多参考图任务。
- 验证只从兼容线路/分组选择 Key、任务结果回填、GET/HEAD/Range、撤权和跨用户隔离。
- 模拟限流、安全轮询、池耗尽、模糊超时和恢复。
- 不读取真实 Key，不连接供应商，不产生费用。

完成自动化后启动新的隔离验收端口，让用户亲自操作管理编辑器和画布。用户验收通过后，才进入下一阶段或真实小额模型调用。

## 11. 首切片不包含

- 管理页面录入、回显或导出 API Key。
- 任意脚本、动态模块、普通用户自定义 Base URL。
- 根据价格自动选择线路。
- 自动抓取供应商模型目录并扩大权限。
- 模糊超时后的自动付费重试。
- Redis 持久化任务队列和多区域任务接管。
- 未经官方合同验证的通用视频、音频或聊天协议。

这些能力必须在本切片稳定并由用户验收后，以独立设计增量加入。
