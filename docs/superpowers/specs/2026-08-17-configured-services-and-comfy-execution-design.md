# 已配置服务、ComfyUI 执行与 Portal 人像复用设计

日期：2026-08-17

状态：按当前用户目标实施

适用仓库：`ai-creation-canvas`

## 1. 交付目标与明确边界

拉取本仓库的维护者应能在不读取相邻 Portal 源码、状态或密钥的前提下，准备仓库外受限配置，完成启动前检查，并在管理员设置正确的服务、Skill 与 Key 后使用：

- 受控 Ark 模型和内置提示词 Skill；
- 已导入、已审核、已派发的 ComfyUI API 工作流；
- Portal 已有的虚拟人人像图片到视频能力。

本切片不配置公网、域名、DNS、真实 API Key、真实 ComfyUI、真实 Portal，也不执行跨服务联调或付费调用。所有网络行为由 `httpx.MockTransport` 和本地临时目录合同测试替代。

浏览器绝不读取、展示、缓存或持久化 Key、ComfyUI 地址、认证头、完整 API 工作流、Portal 内部令牌或其他用户的资源。生产 Canvas 仍只由 Portal 的已登录回环挂载访问。

## 2. 当前事实与缺口

已有工作流库已经提供不可变 revision、导入、预览、导出、启停、受信服务声明和静态无限画布节点；`ComfyHttpWorkflowService` 已实现 `/prompt`、`/history`、`/queue` 的窄适配器及 prompt 归属防重放。然而普通用户 API 仍声明 `EXECUTION_NOT_IMPLEMENTED`，完成的 Comfy 历史也不能转成平台结果。因此“服务器已安装 ComfyUI 即可使用”尚未成立。

已有 Portal 人像适配器已按 `portal-virtual-v1` 进行：安全上传本地受限图片、取得不透明上游资产 ID、owner 请求携带的新鲜 Cookie 轮询、通用视频任务和同源结果代理。它是复用对象，不重写 Portal 人像应用。

已有 Prompt Skill 服务只接受仓库内固定、可溯源的 Skill 指令，并仅在同时设置文本模型 ID 与 `ARK_API_KEY` 时启用。现有生产文档未把这条条件、ComfyUI 认证引用、人像合同、启动前检查和离线冒烟组成一条可执行路径。

## 3. 选型

采用“服务端受控执行 + 不可变 revision + 显式执行配置”的方案。

不采用浏览器直接连接 ComfyUI：它会泄露服务地址/认证边界、绕开用户归属和幂等记录。

不把每个 ComfyUI 节点转换为画布节点：第三方节点、动态端口和自定义前端代码不属于本仓库的扩展边界。

不复制 Portal 人像逻辑：Canvas 仅维持受审计的适配器、所有权映射和合同测试，Portal 仍是人像资产/任务的权威实现。

## 4. 配置与秘密边界

发布包之外的受限目录包含三个普通、非符号链接文件，均由服务账号拥有且为 `0600`：

1. `credential-pools.json`：已有受管模型供应商 Key 池；
2. `comfyui-services.json`：稳定 `service_id`、受信 `base_url`、超时和可选 `auth_header_ref`；
3. 可选的 Portal 服务声明副本：只含挂载、能力和人像 `portal-virtual-v1` 路由，不含 Key。

所有秘密由服务管理器的受限环境文件或秘密管理器提供，绝不出现在命令行、JSON 声明、数据库、日志或浏览器：

- `ARK_API_KEY`：Ark 媒体与提示词 Skill 共用的服务端 Key；
- `AICC_CREDENTIAL_HMAC_KEY`：生产受管模型 Redis 协调的独立随机值；
- `AICC_PORTAL_INTERNAL_TOKEN`：Canvas 验证 Portal 签名身份的内部令牌；
- `AICC_COMFY_AUTH_<REF>`：一个可选 ComfyUI 认证引用的完整 `Authorization` 值，其中 `<REF>` 来自声明的 ASCII 标识并按固定规则转为大写下划线名称。

生产 CLI 接受安全的环境令牌来源；旧的显式令牌参数只保留兼容，不出现在新的操作指引。启动前检查必须验证文件路径/权限、必需环境变量是否存在且满足最小长度、声明语法、静态发布物、提示词 Skill 模型与 Key 的成对关系、ComfyUI 认证引用是否可解析；它不得探测任何外部服务。

## 5. ComfyUI 执行切片

### 5.1 可执行 revision

只有同时满足以下条件的 revision 可以运行：

- 拥有已审核的 API 格式；保存格式绝不自动转换为 API 格式；
- 关联的 `service_id` 已在受信服务配置中声明；
- 管理员已启用模板；
- 管理员为该不可变 revision 保存一个严格验证的执行配置；
- 执行配置要求的节点类型在管理员显式健康检查时兼容。

导入的任意第三方工作流仍可安全预览/导出；缺失执行配置或依赖时只能显示不可运行原因。

执行配置是服务器保存的、可审计的纯数据：公开文字输入、公开图片资产输入、输出选择和对应 API 节点 ID/输入名。它不接受 URL、脚本、节点类型、认证字段、优先级或任意 JSON 合并。每个绑定都要求目标节点和输入已存在于该 revision，允许的值类型与初始 API 值一致；字符串有长度上限，图片只可引用当前用户的 active 自有资产。每一次配置改动创建新的执行配置 revision；已经提交的运行永久引用当时的工作流与配置快照。

首个可交付参数类型为 `text` 和 `image`。图片由服务端从已归属本地资产安全读取，以运行 ID 生成的文件名上传到受信 ComfyUI，再仅把该受信文件名写入受审核的 `LoadImage` 类输入。没有公开绑定的 API 工作流可以作为静态模板运行。视频/音频和第三方专用输入必须在今后的独立配置类型中显式添加，不能退化为任意文件路径或节点参数。

### 5.2 运行、结果与取消

新增独立的 Comfy 运行服务和加法式 SQLite 表，而不把 `ComfyWorkflowServicePort` 伪装为 `GenerationPort`。运行记录包括不透明 `run_id`、owner、模板/revision/执行配置版本、服务 ID、幂等键、上游 prompt ID、状态、不可变请求摘要、结果元数据和最小用量事件；不保存 Key、Cookie、完整提示词、API JSON 或可公开的 Comfy URL。

普通用户 API 仅接受已派发启用的 `workflow_id`、当前/指定获准 revision、受严格 schema 验证的公开输入和幂等键。服务端先验证 owner、配置、资产和兼容性，再原子预留运行；相同 owner+幂等键只返回同一运行。提交到 `/prompt` 后立即持久化 prompt owner。连接中断、持久化失败或任何发送后不明状态都进入 `submission_unknown`，禁止重放。

运行状态使用 `queued`、`running`、`succeeded`、`failed`、`cancelled`、`submission_unknown`。ComfyUI 有服务端认证，不需要浏览器 Cookie 才能轮询；背景轮询只能处理已明确持久化 prompt ID。取消先校验当前 owner 和本地状态，再调用固定 `/queue` 删除路径；取消和轮询均在上游 I/O 前重复检查持久化 prompt 归属。

仅接受 Comfy 历史中受限的标准输出文件描述符（文件名、子目录、类型均严格校验）。服务端通过受信 `/view` 下载它们，限制数量、大小与 MIME，写入 Canvas 的私有结果存储，并只向 owner 返回现有同源受保护结果 URL。历史中的 URL、任意路径、文本、嵌套 metadata 和自定义对象不会回传浏览器。结果、用量和活动记录归属到运行 owner；第二用户对运行、取消与结果均得到 404。

### 5.3 画布与管理 UI

管理员页增加“执行配置”与“可运行性”面板：它只显示安全的端口定义、依赖状态、配置版本和错误码，不显示 API JSON、Comfy 地址或认证信息。管理员可以显式健康检查并启用/停用；服务不可用不影响导入、预览与导出。

静态 `comfy.workflow` 画布节点只能从用户目录选择已派发模板。节点以用户可见输入 schema 生成控件，提交受控运行，按 `run_id` 恢复轮询，并把同源结果填入结果节点。项目持久化仅存稳定 workflow/revision/config ID、公开输入和 run ID；不得存 API JSON、端点、认证或服务端调试字段。

## 6. Portal 人像对标

人像完成条件以 `portal-virtual-v1` 合同和现有 Portal 测试语义为准：

- 仅支持 PNG/JPEG/WebP、10 MiB 以下、无路径跟随的文件；
- 先创建 Portal 资产组，再流式上传；返回 ID/状态必须为不透明且结构正确；
- 本地资产记录与上游资产 ID 原子关联；失败恢复记录不能泄露 Cookie 或内容；
- `video.image_to_video` 仅允许一个人像资产；所有提交、轮询和结果请求携带当次 owner Cookie；
- 401/403 要求 owner 重新登录且绝不持久化 Cookie；失败不重放；
- 结果继续走同源、owner 检查的代理。

本仓库不修改 `ai-generation-portal`。增加的合同测试使用 mock Portal 响应覆盖上游错误文本、组刷新、资源归属、恢复与状态，不打开上游运行状态或真实凭据。

Portal 模式下“向目标用户派发 Comfy 模板”依赖一个独立的已签名 Portal 用户目录 port；在该 port 未定义前，系统维持当前安全行为：允许管理员管理库，但拒绝派发，不接受浏览器声称的用户 ID。该外部接口仅作为部署前置条件和 mock 契约记录，不在本仓库伪造实现。

## 7. 操作指引与离线验收

新增单一操作手册和可提交的零秘密模板，按以下顺序执行：构建发布包、创建服务账号与受限数据/配置/环境目录、复制示例声明、注入秘密、执行离线预检、启动回环服务、管理员导入/配置/启用工作流、普通用户运行最小核心工作流、验证双用户隔离、备份与回滚。

手册明确区分三种结果：

- **通过离线预检**：配置可以被安全加载，未触达外部服务；
- **通过 Mock 冒烟**：Key/Skill/Comfy/Portal 合同由本地模拟服务证明，未发生真实请求；
- **待部署环境联调**：真实 Portal、ComfyUI 或供应商可用性，明确不在本次交付范围。

受控 CLI 使用仓库内核心夹具以及用户显式传入的本地文件进行 Comfy 工作流 round-trip；不把 Downloads 文件作为自动化测试输入或提交内容。

## 8. 验收

自动化必须证明：

1. 缺失/弱/错误权限的秘密或配置在不联网时被拒绝，且错误、日志、API 响应与浏览器状态不泄露值；
2. 正确的 Mock Ark Key + Skill 模型可以使用固定内置 Skill，错误 Key 只得到安全错误；
3. 正确的 Mock Comfy 声明/认证可以提交、轮询、取消并回收受保护结果；重复提交、发送后未知、重启恢复、prompt ID 碰撞、跨用户读取/取消和不安全历史输出均被拒绝；
4. 未启用、未派发、缺少 API revision、缺少执行配置或不兼容服务的模板不能执行；
5. Core、MiniMax、Bernini 三个显式输入的导入预览导出 round-trip 保持节点/连线和规范化 checksum；
6. 人像 mock 合同覆盖上述 Portal 行为，且没有复制 Portal 人像业务代码；
7. 发布包无需 Node，`--check-config`、Python/前端测试、安全扫描、构建和离线双用户冒烟全部通过；生产端口/目录保持未触碰。

## 9. 回滚

所有数据库迁移是加法式。紧急停用顺序为：停用执行配置与模板、停止新 Comfy 运行、让已知运行仅查询或由管理员取消、切回上一发布包和匹配的受限配置。不得删除 SQLite、资产、历史 revision 或凭据文件来“回滚”。
